# v0.6.0：瓶颈原来在 CPU 上

英文对照：`en/vllm/blog/performance/v0.6-throughput.md`  
原文：https://vllm.ai/blog/2024-09-05-perf-update  
2024-09-05。相对 v0.5.3：Llama 8B（1×H100）吞吐约 **2.7×**、TPOT 约 **5×** 更快；Llama 70B（4×H100）吞吐约 **1.8×**、TPOT 约 **2×**。ShareGPT 500 条；TPOT 在 32 QPS 上量。图与附录曲线在原网页。

这是 V1 之前那一轮「把 CPU 从 GPU 路上挪开」的成绩单。V1 公告里的 multiprocessing / EngineCore，是同一条路继续往下挖。

## 诊断

推理是 CPU 和 GPU 的双人舞。GPU 做大矩阵；CPU 负责收请求、调度、准备输入。CPU 跟不上，GPU 就闲着等。

立项那年，优化对象常常是「大模型 + 显存不宽裕的卡」（Llama 13B on A100-40G）。H100 和 GQA / 量化把 GPU 步时压下去以后，CPU 突然变成主角。Llama 3 8B、1×H100 的剖析：

- HTTP API server：**33%**
- 调度（收上一步结果、排下一步、准备输入）：**29%**
- 真正的 GPU 前向：**38%**

两件事：Python 列表和字典好懂、好贡献，但调度和准备输入会慢；许多组件同步执行，因为当年假设「模型一定比 CPU 慢」，也因为 beam search 这类调度好写。GPU 于是经常在门口等。

## 三刀

**API server 拆进程（PR #6883）。** 流式回包在高并发下极吃 CPU：Llama 3 8B 轻载大约 13 ms 一个 token，前端每秒要推大约 76 个对象，再乘上几百并发。API 与引擎同进程就会抢 Python GIL。拆开：校验、tokenize、JSON 在一边，调度和推理在另一边，中间 **ZMQ**。GIL 不再是同一把锁。当时还说 API 路径会继续向离线 batch 的效率靠。

**一次调度、连续跑 n 步（PR #7000，multi-step）。** 调度和准备输入只做一次，模型连跑 `n` 步，GPU 不必每步回头等 CPU。Llama 70B on 4×H100 吞吐大约 **+28%**。基准里他们开了 `--num-scheduler-steps 10`，当时还不是默认。

副作用要记住：当时实现会把多步的 token **成批发回**，用户侧 ITL 会一颠一颠（他们说要改成中间 token 先流回去）；低 QPS 时新请求要等当前 multi-step 跑完，TTFT 会变差。高 QPS 排队延迟为主时，这点不明显。

**异步处理输出（PR #7049 等）。** 从前每步：GPU→CPU，检查 stop，再下一步。detokenize 和字符串匹配随 batch 变胖。现在假定第 n 步没人结束，把第 n 步的输出处理叠到第 n+1 步的 GPU 上。多跑半步的税，换 GPU 利用率。70B / 4×H100 上 TPOT 大约 **−8.7%**。

杂项：对象缓存（吞吐 **+24%**）、CPU→GPU 尽量 non-blocking copy、简单采样走快路径。

## 怎么比的

对手：TensorRT-LLM r24.07、SGLang v0.3.0、lmdeploy v0.6.0a0。数据集：ShareGPT（均 ISL 202 / OSL 179）、prefill-heavy（约 462/16）、decode-heavy（约 462/256）。Llama 3 8B / 70B（没用 3.1，因为当时 TRT-LLM 还不认）。A100 与 H100。指标：TTFT、TPOT、QPS=inf 下的吞吐。

H100 上 ShareGPT 和 decode-heavy，vLLM 自称吞吐最高；prefill-heavy 往往落后——长问短答那一档，当时别的引擎更会切 prefill。附录按 8B/70B × A100/H100 拆开，细节以原文图为准。复现 issue 在 GitHub。

读这一篇，是为了记住一句很难听的话：**卡很快以后，慢的是 Python。** V1 把这句话写成了架构。
