## 诊断

推理是 CPU 和 GPU 的双人舞。大矩阵在 GPU 上；CPU 负责收请求、调度、准备输入。CPU 跟不上，GPU 就闲着等。

立项那年，优化对象常常是「大模型 + 显存不宽裕的卡」（Llama 13B on A100-40G）。H100 和 GQA / 量化把 GPU 步时压下去以后，CPU 突然变成主角。

**Llama 3 8B、1×H100 的剖析：**

- HTTP API server：**33%**
- 调度（收上一步结果、排下一步、准备输入）：**29%**
- 真正的 GPU 前向：**38%**

两件事：

1. **CPU 开销高。** 为了好懂、好贡献，大部分逻辑留在 Python，调度和准备输入用列表和字典。那笔税会显形。
2. **组件同步。** 调度器和 output processor 会堵住 GPU。他们点名两个原因：当年假设「模型一定比 CPU 慢」；beam search 这类调度更好写。GPU 于是经常在门口等。

一句话：**挡住 GPU 的，是 CPU。** v0.6.0 用一个月来砍这笔税。

## 三刀，外加杂项

### API server 拆进程（[PR #6883](https://github.com/vllm-project/vllm/pull/6883)）

OpenAI 协议的校验、tokenize、JSON，在**流式**、高负载下极吃 CPU。例子：Llama 3 8B 轻载大约 **13 ms** 一个 token，前端每秒要推大约 **76** 个对象，再乘上几百并发。

从前 API 与引擎同进程，协程抢同一把 **Python GIL**。

拆开：校验 / tokenize / JSON 在一边，调度和推理在另一边，中间 **ZMQ**。两把 GIL，两坨 CPU 重活彼此隔离。

拆完仍有空间。当时还在做 [PR #8157](https://github.com/vllm-project/vllm/pull/8157)，想让 API 路径靠近**离线 batch** 的效率。

### 一次调度、连续跑 n 步（[PR #7000](https://github.com/vllm-project/vllm/pull/7000)）

调度和准备输入太慢，GPU 步与步之间会空转。**multi-step scheduling**：调度和准备只做一次，模型连跑 `n` 步 GPU。CPU 的税摊到这 n 步上。

Llama 70B on 4×H100 吞吐大约 **+28%**。

基准里开了 `--num-scheduler-steps 10`。**当时还不是默认**；他们说正在把它做成默认。

**当时实现的副作用**（历史，不是今日必真）：

- **ITL 一颠一颠。** 多步的 token **成批发回**，用户侧会忽然接到一串。他们说要改成中间 token 先流回引擎。
- **低 QPS 时 TTFT 变差。** 新请求要等当前这轮 n-step 跑完。`--num-scheduler-steps` 越大，低请求率时 TTFT 越差。附录曲线看的是**高 QPS 的排队延迟**，这点不明显。

### 异步处理输出（[PR #7049](https://github.com/vllm-project/vllm/pull/7049)、[#7921](https://github.com/vllm-project/vllm/pull/7921)、[#8050](https://github.com/vllm-project/vllm/pull/8050)）

旧环：GPU → 拷回 CPU → 检查 stop → 下一步。detokenize 和字符串匹配随 batch 变胖。

新环：把第 `n` 步的输出处理叠到第 `n+1` 步的 GPU 上。**假定第 n 步没人结束。** 税是每个请求**多跑半步**。GPU 利用率补得回来。

70B / 4×H100 上 TPOT 大约 **−8.7%**（原文说 TPOT improved by 8.7%）。

### 杂项

- **对象缓存**（[#7162](https://github.com/vllm-project/vllm/pull/7162)）：请求来了又走，Python 不停分配释放。缓存对象，端到端吞吐 **+24%**。
- **Non-blocking H2D**（[#7172](https://github.com/vllm-project/vllm/pull/7172)）：CPU 可以连发许多 copy，GPU 自己搬。
- **简单采样快路径**（[#7117](https://github.com/vllm-project/vllm/pull/7117)）：常见负载跳过完整的 attention backend / 采样迷宫。

## 怎么比的（当时的快照）

**引擎。** vLLM v0.6.0 对 TensorRT-LLM **r24.07**、SGLang **v0.3.0**、lmdeploy **v0.6.0a0**。别人用默认；vLLM 开 `--num-scheduler-steps 10`。

**数据集**（各 500 条）：

| 数据集 | 形状 |
|---|---|
| ShareGPT | 固定种子随机采样；均 **ISL 202 / OSL 179** |
| Prefill-heavy | sonnet 合成；约 **462** in / **16** out |
| Decode-heavy | sonnet 合成；约 **462** in / **256** out |

**模型。** Llama **3** 的 8B 与 70B。**没用 3.1**：当时 TensorRT-LLM r24.07 / backend v0.11 还不认（[NVIDIA/TensorRT-LLM#2105](https://github.com/NVIDIA/TensorRT-LLM/issues/2105)）。

**硬件。** A100 与 H100。

**指标。**

- TTFT（ms）：均值与标准误。
- TPOT（ms）：均值与标准误。
- 吞吐（请求/秒），在 **QPS = inf**（请求一次性到齐）。

**标题结论。** H100 上 ShareGPT 和 Decode-heavy，vLLM 自称吞吐最高。Prefill-heavy 往往落后——长问短答那一档，当时别的引擎更会切 Prefill。

复现：[vllm-project/vllm#8176](https://github.com/vllm-project/vllm/issues/8176)。

## 附录（图 07–10 的文字）

精确曲线看图。图注原意：

**Llama 3 8B / 1×A100。** ShareGPT 与 Decode-heavy 上 TTFT、TPOT 与 TensorRT-LLM、SGLang 相当。LMDeploy：TPOT 更低，TTFT 普遍更高。吞吐：TensorRT-LLM 最高；vLLM 在 ShareGPT 与 Decode-heavy 上第二。

**Llama 3 70B / 4×A100。** vLLM、SGLang、TensorRT-LLM 的 TTFT/TPOT 相近（LMDeploy 仍是更低 TPOT、更高 TTFT）。吞吐：ShareGPT 上 vLLM **最高**，另外两组打平。

**Llama 3 8B / 1×H100。** ShareGPT 与 Decode-heavy 吞吐当时称 SOTA；Prefill-heavy **落后**。

**Llama 3 70B / 4×H100。** ShareGPT 与 Decode-heavy 吞吐最高（只比 TensorRT-LLM **略高**）；Prefill-heavy **落后**。
