# 参数与实践

指标对齐之后，测试参数必须像你的业务，而不是像别人的博客。下面这些设置，是为了让数字可复现、可比较——也就是让这场考试对所有考生用同一张卷子。

## 业务场景

应用的用法决定 ISL 和 OSL。序列长度影响：输入处理有多快、KV cache 有多胖、输出 token 走得有多累。输入长，prefill 显存和 TTFT 涨；输出长，生成显存和 ITL 涨。先搞清楚你自己的输入输出分布，再谈硬件利用率。否则你是在给邻居的房子做结构计算。

常见量级：

- **翻译**（语言或代码）：ISL 与 OSL 相近，大约各 500–2000。
- **生成**（代码、故事、邮件、检索式写作）：OSL 约 1000，ISL 约 100。短问长答。
- **摘要**（检索、思维链、多轮聊天）：ISL 约 1000，OSL 约 100。长问短答。
- **推理模型**（显式 CoT）：ISL 可以很短，OSL 可到 1000–10000。模型在心里走很远的路，你在外面等。

有生产流量，就用真实 prompt。合成 token 很听话；真实用户会把 system prompt、聊天记录和一篇年报一起塞进来。

## 负载怎么控

**Concurrency N**：N 个并发客户端，每个手里一份在途请求。等价于服务同时在处理的请求数。一份响应收齐，立刻再发一份，系统里永远有 N 份活。

Concurrency 是描述和控负载最常用的语言。它说的是「火上始终有几口锅」，不是「每小时进店多少人」。

**Max batch size**：引擎真正同时在算的那一组。它可以是并发请求的一个子集。若 concurrency 超过 `max_batch_size × 活着的副本`，多出来的请求在队列里等，TTFT 会因为排队涨起来。模型没变慢，门厅变长了。

**Request rate**：按到达率发。恒定速率 `r` 表示每 `1/r` 秒来一个。泊松则规定平均间隔。到达超过吞吐时，在途请求可以无限堆积——像一场永不散场的雨。

AIPerf 两种都支持。**多数基准请用 concurrency**：尺子停在你设定的 N 上，而不会在你不注意时把整条街淹没。

扫描并发：从 1 扫到略大于 max batch。超过 max batch 后请求排队，吞吐通常在 max batch 附近饱和，延迟继续爬。那是曲线告诉你「再加人没有更多菜，只有更长的等待」。

## 其他参数

**`ignore_eos`：** 多数 LLM 会在该停的时候吐 EOS。真实使用应当尊重它。**做基准时设 `ignore_eos=true`**，让模型生成到 `max_tokens`，OSL 才稳定，测量才像测量。生产里让人把话说完；实验室里让钟来喊停。

**采样 vs greedy：** 采样策略会改变生成速度。greedy 取最大 logit，跳过对分布的归一化和排序。同一套 benchmark 里采样方法必须固定。换温度再比速度，是换了风再比帆。
