# vLLM v0.6.0: 2.7× Throughput Improvement and 5× Latency Reduction

## Performance diagnosis

LLM inference is a CPU–GPU duet. The big matmuls are on the GPU; the CPU admits requests, schedules, and prepares inputs. If the CPU cannot schedule fast enough, the GPU sits idle.

Year-one vLLM optimized for relatively **large models on memory-tight GPUs** (example: Llama 13B on A100-40G). Faster H100-class cards plus inference-friendly models (GQA, quantization) shrank GPU step time. CPU work became the bottleneck.

**Llama 3 8B, 1×H100 profile:**

- HTTP API server: **33%** of total time
- Scheduling (gather last-step results, schedule next step, prepare inputs): **29%**
- Actual GPU forward: **38%**

Two root causes:

1. **High CPU overhead.** Most of vLLM stayed in Python with native lists/dicts so the code stayed hackable. That tax shows up in scheduling and input prep.
2. **Synchronous components.** Scheduler and output processor blocked GPU execution. Reasons they named: (a) the old assumption that model execution is always slower than CPU, (b) easier implementation of messy schedules (beam search). GPU waits at the door.

Bottleneck in one line: **CPU overhead that blocks GPU execution.** v0.6.0 is a month of cuts against that.

## Performance enhancements

### Split API server and engine ([PR #6883](https://github.com/vllm-project/vllm/pull/6883))

OpenAI-protocol validation, tokenization, and JSON, especially under **token streaming** at high load, eat CPU. Example: Llama 3 8B under light load ~**13 ms** per token → the frontend streams ~**76** objects/s, worse with hundreds of concurrent requests.

Previously API server and engine shared a process, so those coroutines fought the **Python GIL**.

Split: one process for request validation / tokenize / JSON; another for schedule + infer; **ZMQ** between them (low-overhead). Two GILs, two CPU-heavy components isolated.

They still saw more room on the engine↔HTTP path. Follow-up then: [PR #8157](https://github.com/vllm-project/vllm/pull/8157), aiming to make the API path as efficient as **offline batching**.

### Multi-step scheduling ([PR #7000](https://github.com/vllm-project/vllm/pull/7000))

Scheduler + input prep was leaving the GPU idle between steps. **Multi-step scheduling**: schedule and prepare once, run the model for `n` consecutive GPU steps. CPU overhead is amortized across those steps.

**+28%** throughput on Llama 70B / 4×H100.

Benchmarks used `--num-scheduler-steps 10`. **Not default then**; they were working on turning it on by default.

**Then-current trade-offs** (implementation of that vintage):

- **Bumpy ITL.** Multi-step also **returned output tokens in a batch**. From the user’s side, tokens arrive in clumps. They said they would fix this by streaming intermediate tokens back to the engine.
- **Higher TTFT at low request rate.** A new request cannot start until the current n-step finishes. Larger `--num-scheduler-steps` → worse TTFT when QPS is low. Their plots emphasize **queueing delay at high QPS**, so this effect is not dramatic in the appendix.

### Asynchronous output processing ([PR #7049](https://github.com/vllm-project/vllm/pull/7049), [#7921](https://github.com/vllm-project/vllm/pull/7921), [#8050](https://github.com/vllm-project/vllm/pull/8050))

Old loop: GPU step → copy output to CPU → stop checks → next step. Detokenize + string matching grew with batch size.

New: overlap processing of step `n`’s output with GPU step `n+1`. **Assume nobody finished** on step `n`. Tax: **one extra step** per request. GPU utilization more than pays for it.

**TPOT −8.7%** (they phrased it as TPOT improved by 8.7%) on Llama 70B / 4×H100.

### Miscellaneous

- **Object cache** ([#7162](https://github.com/vllm-project/vllm/pull/7162)): stop allocate/deallocate churn as requests arrive and finish. **+24%** end-to-end throughput.
- **Non-blocking H2D** ([#7172](https://github.com/vllm-project/vllm/pull/7172)): CPU can queue many copies while the GPU copies.
- **Fast path for simple sampling** ([#7117](https://github.com/vllm-project/vllm/pull/7117)): skip the full attention-backend / sampling maze for common workloads.

## Bake-off snapshot (then-current)

**Engines.** vLLM v0.6.0 vs TensorRT-LLM **r24.07**, SGLang **v0.3.0**, lmdeploy **v0.6.0a0**. Others: default settings. vLLM: `--num-scheduler-steps 10`.

**Datasets** (500 prompts each):

| Dataset | Shape |
|---|---|
| ShareGPT | random sample, fixed seed; mean **ISL 202 / OSL 179** |
| Prefill-heavy | synthetic from sonnet; ~**462** in / **16** out |
| Decode-heavy | synthetic from sonnet; ~**462** in / **256** out |

**Models.** Llama **3** 8B and 70B. **Not** Llama 3.1: TensorRT-LLM r24.07 / TensorRT LLM backend v0.11 did not support it yet ([NVIDIA/TensorRT-LLM#2105](https://github.com/NVIDIA/TensorRT-LLM/issues/2105)).

**Hardware.** A100 and H100.

**Metrics.**

- TTFT (ms): mean and standard error of the mean.
- TPOT (ms): mean and SEM.
- Throughput (requests/s) at **QPS = inf** (all requests arrive at once).

**Headline.** On H100, vLLM claimed **highest throughput** on ShareGPT and Decode-heavy for Llama 3. Prefill-heavy often lagged — long prompt, short output was a cut other engines were better at then.

Reproduce: [vllm-project/vllm#8176](https://github.com/vllm-project/vllm/issues/8176).

## Appendix (qualitative, from their plots)

Exact curves live in figures 07–10. Their captions:

**Llama 3 8B / 1×A100.** TTFT and TPOT on ShareGPT and Decode-heavy comparable to TensorRT-LLM and SGLang. LMDeploy: lower TPOT, higher TTFT in general. Throughput: TensorRT-LLM highest; vLLM second on ShareGPT and Decode-heavy.

**Llama 3 70B / 4×A100.** vLLM, SGLang, TensorRT-LLM similar TTFT/TPOT (LMDeploy again lower TPOT, higher TTFT). Throughput: vLLM **highest on ShareGPT**, comparable on the other two.

**Llama 3 8B / 1×H100.** SOTA throughput on ShareGPT and Decode-heavy; **lower** on Prefill-heavy.

**Llama 3 70B / 4×H100.** Highest throughput on ShareGPT and Decode-heavy (only **marginally** above TensorRT-LLM); **lower** on Prefill-heavy.

## Conclusion, then-current call to action, events

They treated 1.8–2.7× as a checkpoint, not a ceiling: harden the new features for production, keep widening models/hardware/features, and simplify the core so more people can contribute (the V1 rewrite).

Install pointer then: docs getting-started. Contact: `vllm-questions@lists.berkeley.edu`. Community: [roadmap.vllm.ai](https://roadmap.vllm.ai/), GitHub good-first-issues, X `@vllm_project`. Biweekly office hours (Neural Magic); the next one after this post was a deep dive into these enhancements.
