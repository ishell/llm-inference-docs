# vLLM v0.6.0: 2.7× throughput, 5× TPOT

2024-09-05 vs v0.5.3. Llama 8B 1×H100: ~**2.7×** throughput, ~**5×** TPOT. Llama 70B 4×H100: ~**1.8×** throughput, ~**2×** TPOT. ShareGPT 500 prompts; TPOT at 32 QPS. Plots on the official page. Pre-V1 “get CPU off the GPU’s path.”

## Diagnosis (Llama 3 8B, 1×H100)

- HTTP API server **33%**
- Scheduling + input prep **29%**
- GPU forward **38%**

Python-native structures (easy to hack) + synchronous components (old assumption: the model is always slower than the CPU). GPU waits.

## Three cuts

**Split API server (PR #6883).** Streaming under load fights the GIL if API and engine share a process. Validate/tokenize/JSON in one process, schedule/infer in another, **ZMQ** between.

**Multi-step scheduling (PR #7000).** Schedule once, run `n` GPU steps. +**28%** throughput on 70B / 4×H100. Benchmarks used `--num-scheduler-steps 10`. Trade-offs: batched token returns (bumpy ITL); higher TTFT at low QPS (new request waits for the current n-step).

**Async output processing (PR #7049+).** Overlap detok/stop-checks of step n with GPU step n+1. Assume nobody finished — one extra step of tax. TPOT **−8.7%** on 70B / 4×H100.

Misc: object cache (+**24%** throughput), non-blocking H2D, fast path for simple sampling.

## Bake-off snapshot

TRT-LLM r24.07, SGLang v0.3.0, lmdeploy v0.6.0a0. ShareGPT / prefill-heavy / decode-heavy. Llama 3 8B & 70B (not 3.1 — TRT-LLM then). vLLM claimed top H100 throughput on ShareGPT and decode-heavy; often behind on prefill-heavy. Reproduce via their GitHub issue.
