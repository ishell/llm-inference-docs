## TL;DR

Disaggregated **4P1D** on 24 B300. Production SLA: **mean TTFT ≤ 2.5 s**, **mean TPOT ≤ 20 ms**. Starting point on the same hardware: mean TPOT nearly **40 ms** at 16K input — about twice the SLA. Journey **40 ms → 17 ms**. The parallelism they **shipped is not** the highest raw throughput. Reproducible `vllm serve` at the end.

**Figure.** GLM-5.2-NVFP4 on 24× B300, 4P1D: total throughput, output throughput, TTFT and TPOT across input lengths 8K–256K.

## 1. Why We Optimized for SLA Compliance, Not Peak Throughput

In colocated serving, Prefill chunks interleave into Decode batches. Every long prompt entering a batch stretches **ITL** of every request already decoding. TPOT tail then becomes a function of the incoming prompt-length distribution — something the serving system does not control. Disaggregation takes Prefill off the Decode critical path, so TPOT is a function of Decode batch composition alone. That is why a tight TPOT SLA is achievable, and why this post treats **P/D as the starting point**, not one optimization among many.

Production is not accepted on peak throughput. The question is how much traffic the system can sustain **without** violating latency:

- Typical context: **16K–256K**
- **Mean TTFT ≤ 2.5 s** — delay from user action to first visible token
- **Mean TPOT ≤ 20 ms** — roughly 50 tokens/s streaming; below that, reading degrades
- Subject to those two hard constraints, maximize throughput

Batch size was **not** fixed. Load is a request rate; concurrency is whatever that rate produces under the SLA. Prefill cost grows with context, so concurrency settles lower as input grows: roughly **700** concurrent at 8K, **300** at 16K, **25** at 256K, under a `--max-concurrency 1024` cap.

A config that gains 30% throughput but pushes mean TPOT past the SLA is not useful. Section 4 is a representative example.

GLM-5.2 is a 744B MoE with 40B active, DSA sparse attention, native MTP. vLLM already supports all three. The work was combining them with P/D, then tuning parameters, topology, and scheduling around those SLA targets.

## 2. Starting Point: Improving Decode Performance under P/D Disaggregation

Prefill already met its target with TTFT headroom. Bottleneck was Decode: 16K in / 1K out, mean TPOT close to **40 ms**, substantial P99 jitter.

### 2.1 Root Cause: Mixed Batches at the P/D Handoff

After KV handoff through KVConnector, the first Decode step needs **one** token. Existing MTP requests on that Decode node already run **1 + N** per step. Different shapes → mixed batch → drops the uniform-decode full-CUDA-Graph fast path onto piecewise / eager.

DP amplifies it. CUDA Graph mode and padding coordinate across ranks: **one** rank receiving a newly transferred request pulls **all** ranks onto the slow path. In steady-state P/D, new requests arrive continuously, so the slow path is constant.

### 2.2 Optimization: Speculative Padding on the Decode Side

On the first Decode step after arrival, dummy speculative tokens pad the shape to **1 + N**, matching in-flight Decode. Uniform Decode, full CUDA Graph stays on.

No need to transfer generated or draft tokens from Prefill. Merged in [PR #45237](https://github.com/vllm-project/vllm/pull/45237).

### 2.3 Performance Gain

Mean TPOT **~40 ms → ~22 ms** — the single largest cut of the whole effort.

Broader lesson for P/D + speculative decoding: the largest loss may not live in any kernel. It can sit at the **boundary** between subsystems, where small inconsistencies in request state, scheduling shape, and CUDA Graph mode are amplified by DP scale and continuous traffic.

## 3. Further Decode-Side Optimizations

At 22 ms they were close to the SLA with no safety margin.

### 3.1 Model Runner V2: 11% Lower TPOT

MRV2 is default for dense models since v0.25.0. GLM-5.2 is MoE — **not** default. Explicit: `VLLM_USE_V2_MODEL_RUNNER=1`.

On their Decode config, MRV2 cut TPOT ~**11%** vs MRV1. Beyond a shorter path:

1. [PR #47285](https://github.com/vllm-project/vllm/pull/47285) — GLM-5.2 DSA indexer Prefill-metadata kernel in startup warmup, so the first production request does not trigger Triton JIT. Easy to miss in benches (warmup absorbs it); production sees a cold-start spike after every rolling deploy.
2. [PR #46448](https://github.com/vllm-project/vllm/pull/46448) — local argmax reduction for multi-GPU MTP. `use_local_argmax_reduction`: draft generation no longer AllGathers full-vocab logits; TP communication volume ~**2 × TP size** instead of vocab-sized. MTP, EAGLE, DFlash, and other speculators under MRV2 benefit.
3. [PR #45953](https://github.com/vllm-project/vllm/pull/45953) — dynamic speculative lengths with full CUDA Graphs; fewer graph misses and eager fallbacks when draft length changes.

### 3.2 All-to-All Backend: 4% Lower TPOT

Decode runs **DEP8**; expert dispatch/combine sits on the critical path. FlashInfer NVLink A2A `flashinfer_nvlink_two_sided` cut TPOT another **~4%**.

Newer `flashinfer_nvlink_one_sided` is expected to do better. This post keeps two-sided because that is what they **measured**.

### 3.3 CUDA Graph Mode

Decode: `--compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}'` with `--max-num-batched-tokens 1024`. Decode does not need Prefill-shaped graphs. `FULL_DECODE_ONLY` covers the Decode path and cuts startup compile time.

### 3.4 MTP Speculative Decoding

Decode `num_speculative_tokens=3`; Prefill `1`. (MTP only becomes cost-effective on GLM-5.2 together with IndexerCache, §5.) Prefill should hand off KV fast — deeper speculation buys little. Decode sits on the latency path, where deeper speculation amortizes per-token cost **if** acceptance stays high.

## 4. Prefill Parallelism: Why We Did Not Choose the Highest-Throughput Configuration

Compared several Prefill strategies at 8K and 32K. Different GPU counts → **TGS** (throughput per GPU) is the metric.

**Figure.** Per-GPU Prefill throughput for four parallelism strategies, 8K and 32K.

In absolute tokens, **TP1 DP4 EP** is the fastest instance — **47,806 tok/s** at 8K — only because it uses twice as many GPUs; per GPU it is second. Two conclusions:

1. **TP2 + EP performed worse than plain TP2.** At two GPUs, all-to-all overhead exceeds EP’s benefit. EP needs enough experts across enough devices to amortize communication.
2. **TP1 DP2 EP had the best TGS; they shipped TP1 DP4 EP.**

Production parts ways with benchmark chasing. Best per-GPU efficiency left only two GPUs per instance — too little KV for GLM-5.2’s **1M** context. They would not give up that feature for an **~8%** TGS edge, so **TP1 DP4 EP**: trade ~8% per-GPU efficiency for four-GPU KV capacity.

## 5. MTP + IndexerCache: How We Improved the Acceptance Rate

This deployment turned on three relatively new capabilities at once: P/D, MTP, MRV2. Less-exercised combination; long-tail issues showed up. Most fixes report-to-release in a few days; **v0.26.0** already has them.

### 5.1 IndexerCache: Making MTP Cost-Effective with DSA

IndexerCache ([PR #44420](https://github.com/vllm-project/vllm/pull/44420)) is **not** a conventional KV cache — it reuses Top-K sparse indices from the DSA indexer. Naive: rerun the indexer every MTP draft step; sparse-retrieval cost grows with context and can eat speculation. `index_share_for_mtp_iteration`: first draft step computes Top-K; later draft steps reuse. Prerequisite for MTP to be worthwhile on GLM-5.2 at all.

Three follow-ups that stabilized acceptance under high concurrency:

- [PR #45895](https://github.com/vllm-project/vllm/pull/45895) — indexer init when Top-K layers are skipped; GLM-5.2 MTP normalization loop. On GLM-5.2-FP8 TP=8: mean accepted length ~**3 → ~4**, average acceptance ~**60%**, IFBench held at **74.62**.
- [PR #47238](https://github.com/vllm-project/vllm/pull/47238) — shared index buffer layout for batched requests: after the first draft step, keep only Top-K for each request’s **final** query token. The step that extended index sharing from single-request to high-concurrency batching.
- [PR #47448](https://github.com/vllm-project/vllm/pull/47448) — MTP loop reuses post-final-norm hidden state.

IndexerCache is not merely a compute save. It is how MTP acceptance holds up under high concurrency.

### 5.2 Two Additional Fixes for the Combined Configuration

**MRV2 scheduling classification.** Excessive TPOT variance under a specific bench pattern: [Issue #47239](https://github.com/vllm-project/vllm/issues/47239). Speculative-decoding steps classified as Prefill → slower path. [PR #47381](https://github.com/vllm-project/vllm/pull/47381).

**Lookahead for async KV loading in P/D.** [PR #46694](https://github.com/vllm-project/vllm/pull/46694) — Decoder waits until remote KV transfer completes before allocating speculative-token slots; handles a final **partial** KV block. Specific to P/D × speculative decoding.

Both in v0.25.0+.

### 5.3 Accuracy Validation

Public benches with the final config (NVFP4 + MTP + P/D):

| Test Item | Score |
| --- | ---: |
| AIME 2025 | 86.67 |
| GPQA | 92.89 |
| LongBench V2 | 64.01 |

## 6. Upstream Progress

Tracking issue: [Issue #46654](https://github.com/vllm-project/vllm/issues/46654).

**Secondary tier for P/D.** [PR #42285](https://github.com/vllm-project/vllm/pull/42285) — unified CPU KV-cache layout as an intermediate layer. `TieringManager` coordinates primary cache and P/D connector. Merged v0.25.0.

**PCP virtual batching for long-context Prefill.** [PR #46570](https://github.com/vllm-project/vllm/pull/46570) — split requests into virtual batch rows across context-parallel ranks; aggregate only MLA latent cache and DSA indexer cache. Initial 4-GPU GLM-5.2-NVFP4 / 32K Prefill: TP=2 + PCP=2 raised prompt throughput **~20.1K → ~27.3K tok/s**. Merged `main` 2026-07-19; next release. KV capacity is exactly why they rejected the TGS-optimal config in §4 — PCP may reopen that trade.

## 7. Observability: Verifying the SLA after Production Launch

A bench pass is not production-ready. P/D observability is harder: latency splits across two pools. TTFT mostly Prefill; TPOT Decode; KV transfer in between. Users see one symptom — the service got slower.

Prometheus + Grafana. Watch:

- **Per-pool TTFT and TPOT percentiles**, not only e2e aggregates. First place to decide Prefill vs Decode.
- **MTP acceptance rate and mean accepted length.** No error when acceptance falls; TPOT just degrades. First dashboard for any Decode anomaly. Treat MTP acceptance as a **first-class alert**.
- **KV-cache utilization vs GPU utilization**, both pools. Independent scaling is the point of P/D; relative curves are the scaling signal.
- **KV-transfer latency and queue depth** — whether the inter-node network is the bottleneck.

### 7.1 A Problem Visible Only during Long-Running Stability Tests

Short benches validate performance, not long-term stability. Multi-day soak: host RSS grew **linearly** over tens of hours, no plateau.

**Figure.** Grafana Memory Usage (WSS): vLLM container memory **~721 GiB → ~800 GiB** over tens of hours.

Why benches missed it:

- Slow growth, hours-scale. `vllm bench serve` lasting seconds/minutes cannot see it.
- Host memory, not GPU. Every GPU metric looked normal.
- `EngineCore` calls `gc.freeze()` at startup — leaked objects never appeared in `gc.get_objects()` or `tracemalloc`; looked like allocator fragmentation.

Reported in [PR #47723](https://github.com/vllm-project/vllm/pull/47723); maintainer folded into [PR #44490](https://github.com/vllm-project/vllm/pull/44490).

Root cause: producer/consumer gating mismatch. [PR #35219](https://github.com/vllm-project/vllm/pull/35219) introduced `SingleTypeKVCacheManager.new_block_ids` to clear Mamba SSM cache. Entries recorded by KV-cache spec type (`FullAttentionSpec`, `MLAAttentionSpec`, …) but **cleared only if the model had Mamba layers**. Models without Mamba — most standard attention, and GLM-5.2 with MLA — recorded every block allocation and never drained. Unbounded growth with request volume. Fix: drain `take_new_block_ids()` **unconditionally** every schedule step; use the result only when clearing is required. Mamba behavior unchanged.

## 8. Complete Deployment Recipe

### 8.1 Environment

| Deployment | Configuration |
| --- | --- |
| Hardware | 3 × 8 B300 (24 GPUs) |
| Model | GLM-5.2-NVFP4 |
| Topology | 4 Prefill (TP1 DP4 EP, 4 GPUs each = 16) + 1 Decode (TP1 DP8 EP = 8) |
| KV Transfer | NIXL |

### 8.2 Prefill Node

```bash
export VLLM_USE_V2_MODEL_RUNNER=1

vllm serve /mnt/model/glm/GLM-5.2-NVFP4 \
    --trust-remote-code \
    --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_producer"}' \
    --chat-template-content-format=string \
    -ep \
    -tp 1 \
    -dp 4 \
    --tool-call-parser glm47 \
    --enable-auto-tool-choice \
    --reasoning-parser glm45 \
    --gpu-memory-utilization 0.92 \
    --enable-prompt-tokens-details \
    --speculative-config='{"method":"mtp","num_speculative_tokens":1}' \
    --shutdown-timeout 300 \
    --fingerprint-mode=none
```

### 8.3 Decode Node

```bash
export VLLM_USE_V2_MODEL_RUNNER=1

vllm serve /mnt/model/glm/GLM-5.2-NVFP4 \
    --trust-remote-code \
    --chat-template-content-format=string \
    --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_consumer"}' \
    --compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}' \
    --max-num-batched-tokens 1024 \
    -ep \
    -tp 1 \
    -dp 8 \
    --tool-call-parser glm47 \
    --enable-auto-tool-choice \
    --reasoning-parser glm45 \
    --gpu-memory-utilization 0.90 \
    --enable-prompt-tokens-details \
    --all2all-backend=flashinfer_nvlink_two_sided \
    --speculative-config='{"method":"mtp","num_speculative_tokens":3}' \
    --shutdown-timeout 300 \
    --fingerprint-mode=none
```

### 8.4 Benchmark Methodology

`vllm bench serve` random dataset. **No** prefix-cache hits — TTFT is worst-case, compute-only. Fixed `--request-rate` = target TPS / (input_len + output_len) × a tuning factor.

```bash
vllm bench serve \
  --backend openai-chat \
  --model /mnt/model/glm/GLM-5.2-NVFP4 \
  --endpoint /v1/chat/completions \
  --dataset-name random \
  --random-input-len 16384 \
  --random-output-len 1000 \
  --request-rate <target TPS / (input + output) × tuning factor> \
  --percentile-metrics ttft,tpot,itl,e2el \
  --metric-percentiles 50,90 \
  --save-result
```

## 9. What Comes Next

Forward-looking, not measured in this post.

**First, cheaper target forwards.** Beyond GEMM, Attention, Indexer: PDL, persistent kernels, localized megakernels, coordinated compute/comm across MoE Dispatch, Expert GEMM, Combine. Across nodes: WideEP, hierarchical all2all, overlap of inter-node comm and compute. Shorten the e2e critical path of one Decode step.

**Second, model–runtime co-optimization for speculative decoding.** Stronger drafters (DSpark) on broader data. Runtime: dynamic speculative decoding, per-request proposal lengths, compact verification. The draft model sets how far you can predict; the serving runtime sets how far prediction is economical.

PCP virtual-batch from §6 is already on `main`. Next: whether it removes the KV-capacity vs per-GPU-efficiency trade in §4.
